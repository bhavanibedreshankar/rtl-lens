In rtl/matrix_engine/pe.sv, `product` is declared as `logic signed [ACCUM_WIDTH-1:0]` (32-bit) but is assigned the result of `$signed(a_in) * $signed(weight_reg)`, an 8x8-bit signed multiply that only produces a 16-bit result. This corrupts the sign of negative products before they're summed into acc_in on line 44, causing incorrect accumulation results — exactly matching the observed mismatches where RTL values differ from golden values in sign/magnitude (e.g. rtl=0xffffffe5 vs golden=0x00000062, rtl=0x00000069 vs golden=0x00000081). The fix is to sign-extend each operand to the full ACCUM_WIDTH before multiplying, so the multiplication is performed and produced at the full 32-bit width with correct sign extension throughout.

Hypothesis / root causertl/matrix_engine/pe.sv:63
Confidence
61%

pe.sv line 63 computes the 8x8 signed product and assigns it directly to `product`, which is declared as a full ACCUM_WIDTH (32-bit) signed logic vector. In SystemVerilog, assigning a narrower signed expression to a wider signed target via a continuous assignment does NOT automatically sign-extend based on the narrower expression's own width in all synthesis/simulation contexts consistently -- specifically here, the right-hand-side expression `$signed(a_in) * $signed(weight_reg)` is a 16-bit-wide signed value (product of two signed 8-bit operands), but because it's used directly as an assignment RHS to a 32-bit target, the intermediate result's width in the multiplication is determined by context rules that make this fragile/incorrect: negative 16-bit products end up zero-extended into the upper 16 bits of the 32-bit `product` register instead of sign-extended, turning small negative partial products into huge positive 32-bit numbers before they're added to acc_in on line 44. This matches the observed failure signature exactly: some result cells are far too large/positive (e.g. rtl=0x00000069 vs golden=0x00000081 direction aside, and more tellingly rtl=0xffffffe5 vs golden=0x00000062 shows sign flips), consistent with corrupted sign extension of the multiply propagating through the systolic accumulation chain across K and rows. The minimal fix is to compute the product into an explicitly-sized 2*OPERAND_WIDTH-bit signed intermediate and then explicitly sign-extend that intermediate up to ACCUM_WIDTH before it participates in the sum, removing any ambiguity/mistake in the width-extension of the signed multiply result.
